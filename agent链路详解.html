1 它到底是不是一个 agent

是。判据不是它会聊天、也不是它自称 agent，而是代码里这三样东西同时存在：

判据一：循环。有一个 while 反复把「模型的上一次输出」变成「下一次输入」，而不是单问单答。
agents.py:545

判据二：动作空间。模型输出的不是给人看的文字，而是可执行的结构（工具名 + 参数），由本机真正执行。
agents.py:1361 → tools.py:246 → tools.py:228

判据三：终止条件。有明确的结束信号（final_answer）和一个兜底上限（max_steps），否则会永远问下去。
agents.py:583 / 591 · agents.py:606-607

三条都在，所以它是 agent；缺任何一条，它就退化成一个「带 prompt 模板的接口调用」。市面上很多号称 Agent 的东西确实只有模板没有循环。

但今天要看的是另一个变化：框架的三判据一条没动，动的是循环外面。现在这一份代码在循环的上面和里面各装了阻塞点：

  • 计划开工前，人批一份计划 ← my_ui.py:1110 / 1139
  • 每一次「会动东西」的调用前，人批一张卡 ← my_ui.py:920 / 951
  • 同名同参第二次不再执行，挡够三次直接把整题收掉 ← my_ui.py:993 / 1030 / 1068

这三层都不在 smolagents 源码里，是 OpsUI 用「覆盖实例方法」的写法装上去的，一行 src/smolagents/ 都没改。 所以下面的 21 站分成两半读：第 5–12、18–19 站是框架的循环，第 1–4、7、15–17 站是人装在循环外面的东西。

1.2 能力换了，边界必须跟着换

不是「加了工具」就完了。这一轮真正花时间的是边界跟着改了三处：

  • 审批名单不能写死。GATED_TOOLS 只有 ("write_file", "run_python") （my_ui.py:42），而 MCP 工具是运行时才知道挂没挂上，所以名单现拼： my_ui.py:907-918。把运行时结果写回常量，下一次构造就会读到上一轮的名单。
  • 出网的口子从「结构上不可能」变成「每发都要人批」。旧文档里那句「它没有联网能力」已经不成立： fetch 真能出网。给它兜底的是挂载白名单（my_mcp.py:45-60）、 危险名正则（my_mcp.py:74-77）和 30 秒外部调用超时（my_mcp.py:41 / 136）。
  • 每一次调用都要留痕。my_audit.py:52 / 83 / 105 那三段 JSONL， 挂在查重层而不是审批层，理由写在 my_ui.py:1042-1043：只读那五只手不过门， 挂在审批层就等于它们一条不记。

还有一条没做完，必须写在这儿而不是藏在最后：run_python 现在绕过了 guarded()（my_coding_agent.py:262）。read_file 走 my_coding_agent.py:111-148 那套路径判定，但模型可以让 run_python 里的代码自己 open(".env")——审批卡拦得住「它想跑」，拦不住「跑起来之后读到什么」。 这是当前真实的 P0，任务清单里的 #8，尚未修。

2 一次提问的完整旅程（21 站）

按你实际点发送之后的顺序走，每一站给真实代码位置。旧版只有 13 站，多出来的 8 站全是这一轮装上的东西。

2.1 外壳：从回车到 worker 起转（站 1–4）

  1. 1
    你敲回车，接住它的是你自己的 UI，不是 GradioUI 的那条 for my_ui.py:2180 / 1798

    create_app()（my_ui.py:2180）自己搭界面，提交走 _respond()（my_ui.py:1798），它返回的是一个 8 元组——聊天流、状态条、计划面板、 待批卡、下拉框一起更新。my_ui.py:2300 那行 ui = OpsUI(agent, file_upload_folder="./data") 是唯一的入口，launch 只绑 127.0.0.1:7860、不开 share（my_ui.py:2303-2305）。

    旧版第 1 站写的是「GradioUI 的提交回调里就是一句 for event in self.agent.run(...)，它没有处理逻辑」， 这句话现在是错的。框架那句 for 还在 gradio_ui.py:388-389，但 OpsUI 继承了它却没有沿用它的事件循环——它自己起了线程和队列（第 4 站），否则审批一阻塞就死锁。 「UI 不含任何 agent 逻辑」在 v1 成立；现在这个 UI 是整条链路里最厚的一层（2315 行）。

  2. 2
    本题的历史从 sqlite 里读回来，不是从进程内存 my_ui.py:1716 / 1743 / 741

    _bind_memory()（my_ui.py:1716）把选中的会话号 sid 绑到这次问答上， _session_steps()（my_ui.py:1743）把落盘的步骤读回来。落盘那一写在 my_ui.py:1914：self.hist.save_memory(sid, encode_memory(mem.steps))。

    • 库文件：my_ui.py:33 .agent-history.sqlite3，和代码同目录。
    • 编解码：encode_memory() my_ui.py:171 / decode_memory() my_ui.py:212； 写出去的是 MEM_FMT = "v2"（my_ui.py:102），读的时候同时接受 v1（my_ui.py:107）。
    • 存哪些字段由 MEM_FIELDS 点名（my_ui.py:108）——不含 model_input_messages。 这一点要和第 11 站连着看：框架把「真正喂给模型的原文」存在那格里，你两份落盘都没存它。

    框架侧的 memory 本身很薄：AgentMemory 就是系统提示词 + 一个 steps 列表 （memory.py:214-232），reset() 只是把列表清空。

  3. 3
    换题开局：七本账一起清 my_ui.py:1557-1585

    每次新提问，_stream_response() 先做清算，再挂 worker。这七笔账每一笔都对应一个踩过的坑：

    my_ui.py:1560-1585（顺序就是执行顺序）
    self._settle_all("cancelled")          # :1560 上一题遗留的未批项先结算
OpsUI._ap_cards.clear()                # :1565 卡片登记表（D8：留着就会去改已经不在屏上的对象）
OpsUI._pending_wait = 0.0              # :1568 V8 没人领走的审批等待

    :1576 那一行是整个审计链的关键。它是唯一一处「UI 线程已经知道本题 sid、worker 线程还没起」的时刻。 审计是在 worker 线程里写的（第 15 站），跨线程拿 self._sid 就会串题。

  4. 4
    起一条 worker 线程消费生成器，UI 这边每 0.25 秒取一次 my_ui.py:1532 / 1588 / 1601

    这是这一轮结构上最大的一处改动，理由就一句：审批是阻塞的，而 gradio 是同步往前推生成器的。 工具卡在 forward 里等人点按钮，那条生成器就永远 yield 不出审批卡，界面永远不会出现「允许/拒绝」——死锁。 注释原话在 my_ui.py:1535-1537。

    my_ui.py:1539
    inner = self.agent.run(task, images=files, stream=True, reset=self.reset_agent_memory)

    reset 用的是 GradioUI 的默认 False（gradio_ui.py:310 / 317）， 也就是同一个问题内的历史一定带着。取舍在代码注释里写得很清楚 （my_ui.py:1719 / 1724）：不传 reset=True，因为那会连 monitor 一起清零 （agents.py:478-480），「进程累计」这个口径就废了——跨问题的上下文现在由 sqlite 负责（第 2 站）， 不用牺牲累计口径去换。

    worker 抛出的异常不往外冒，塞进队列由 UI 侧原样重放（my_ui.py:1545-1546）； finally 里那句 inner.close() 要自己接住 RuntimeError （my_ui.py:1548-1554），因为上游 _run_stream 的 finally 里还有一次 yield。

2.2 循环、计划与记忆（站 5–12）

  1. 5
    run() 建立任务外壳，步数上限取构造时的 8 agents.py:436 / 468

    字符串包成 TaskStep 塞进 memory，然后：

    agents.py:468
    max_steps = max_steps or self.max_steps

    你没在 run() 里传，所以用的是 my_agent.py:94 的 max_steps=8；框架默认是 20 （agents.py:300）。旧版写的「你设 6」已经改了，而且这个数现在不是孤零零的一个熔断值， 它和第 6 站绑在一起。

  2. 6
    计划先于行动：每题恰好一份 PlanningStep agents.py:550-552 → 741

    框架只在 planning_interval 不为 None 时才产出 PlanningStep，判据是：

    agents.py:550-552
    if self.planning_interval is not None and (
    self.step_number == 1 or (self.step_number - 1) % self.planning_interval == 0
):

    PLANNING_INTERVAL = 8（my_agent.py:44）和 max_steps = 8 同高， 算术写在 my_agent.py:32-33：下一次重规划落在第 9 步，而 while step_number <= max_steps 在第 9 步之前就退出了。所以题内不会重规划，每题只出一份计划—— 这不是巧合，是为了让「计划可见」这件事的成本恰好等于一次模型调用。

  3. 7
    人装的闸：计划批不批，在这里停下 my_ui.py:1110 / 1139

    装法是覆盖实例上的 _run_stream。这条路是唯一的，因为 run(stream=True) 直接 return self._run_stream(task=..., max_steps=..., images=...)（agents.py:496， 方法定义在 agents.py:540），实例属性优先于类上的方法，所以拦得住，且一行 src/smolagents/ 都不改。 包装里只多一句 _plan_gate，其余原样转发，连 ChatMessageStreamDelta 也照转—— 计划正文照样一个字一个字流出来，面板是流完之后那份的常驻视图。

    _plan_gate()（my_ui.py:1139）和工具审批共用同一套东西：D7 的临界区 （入队和「本轮已被停止」一起判，my_ui.py:1148-1149）、V8 的等待过账 （my_ui.py:1153-1154）、decision 的五个取值、同一对 ✔/✖ 按钮。 不同的只有落场：工具被拒本题还在跑，计划被否这一题就没开工——所以这里抛异常出去， PlanDeniedError 在 my_ui.py:588。取消这一档抛的是和框架同款的 AgentError("Agent interrupted.")，好让两条路对得上（框架那句在 agents.py:546-547）。

    【待补】批准／拒绝这个决定不进模型记忆，只进审计和界面。也就是说你拒了一份计划之后， 模型那边并不知道「这份计划被否了」——下一问它看到的还是全新开局。这在设计上可以辩解（换题即换事）， 但文档不该假装它不存在。

  4. 8
    进入主循环 agents.py:545-547
    while not returned_final_answer and self.step_number <= max_steps:
    if self.interrupt_switch:
        raise AgentError("Agent interrupted.", self.logger)

    整条链路的心脏。条件里那两个变量一个由模型决定（拿到 final_answer 才置真），一个由本地计数决定， 模型无法自己延长循环——它只能在这 8 步里想办法。那句 interrupt_switch 现在不只给人用： 查重熔断也调它，而且它有个洞，第 15 站专门讲。

  5. 9
    把历史压成消息：每走一步整段重发 agents.py:758
    def write_memory_to_messages(self, summary_mode: bool = False) -> list[ChatMessage]:

    memory 里所有 system prompt / TaskStep / llm_output / action / observation 全部摊平成消息列表。 大模型没有「会话状态」，服务端不记你上一轮，所以每一步都要把整段历史重新发一遍。

    这一步的规模由你能塞进上下文的东西决定，而那些上限全是自己写的：

    • 一次 read_file 最多 MAX_LINES = 300 行（my_coding_agent.py:107 / 165）。
    • grep_files 跳过 MAX_BYTES = 200_000 以上的文件（my_coding_agent.py:108 / 211）。
    • fetch 的正文整段进上下文，默认 5,000 字符——这条写在 my_mcp.py:55-58 的风险描述里， 上限在 MCP server 自己那边，不在你代码里。

    尺子那一份全量的实测是 401,273 个输入 token（见 §3.2），这就是「每步重发」四个字的真实价格。

  6. 10
    系统提示词当场生成：工具定义即接口契约 agents.py:1265

    ToolCallingAgent.initialize_system_prompt() 把工具的名字、描述、参数 JSON schema 一起写进系统提示词。你在工具类里写的那几个字符串先被序列化给模型看，模型对工具的全部认知就来自它们。

    这一轮多加了一条守卫：「不改提示词」现在是被测出来的，不是靠自觉。 v18_test_dup.py 的 prompt_surface()（验收脚本/v1.8/v18_test_dup.py:464） 把提示词面抽出来和快照逐字比对（同文件 :492-493 那条 9a 断言）。 注意它比的是 .rollback/v1.8/after-p0abc 那份快照——快照已被覆盖，这条守卫目前是在跟一把旧尺子比， 属于本轮要处理的事项（见文末）。

    还有一句容易漏的：my_agent.py:98 那个 description= 模型读不到。 顶层 ToolCallingAgent 的 description 只在 describe() 里用，那是给「被托管的子 agent」看的； 实测 '读代码' in agent.system_prompt → False（注释在 my_agent.py:99-101）。 真正给模型念的能力边界在各工具的 docstring 和 guarded() 的报错里。

2.3 出网那一站，和它的三道刹车（站 13）

  1. 13

6 四个实验的现状

6.1 E1 给它一个读文件的工具 —— 已做，而且比当时写的多

旧版这里是一段「建议加这个类」的代码。现在它是 my_coding_agent.py 的五个函数 （:152 / 176 / 195 / 231 / 262）。当时那句「路径检查不是可选的」也落成了 guarded()（:111-148）+ DENY_NAMES（:105）。 留了一个尾巴：第 1.2 节那条 run_python 绕开它的洞。

6.2 E2 看熔断长什么样 —— 数值变了，而且现在多一层耦合

当时是「把 6 改成 1」。现在是 max_steps=8（my_agent.py:94）， 看到的仍然是 state="max_steps_error"（agents.py:524 / 606-607）。 但要提醒一句：它和 PLANNING_INTERVAL（my_agent.py:44）是绑的—— 两者的相等关系正是「每题恰好一份计划」的来源（站 6）。只改小 max_steps 会连带改变计划的出题节奏， 不再是单变量实验；想只看步数熔断，两个一起改。

6.3 E3 让 token 不再累加 —— 已落地，但取舍换了个形态

旧版让你去开 GradioUI(reset_agent_memory=True)。现在这条路已经不是主路：OpsUI 不走框架那条 for， 自己在 my_ui.py:1539 调 agent.run(..., reset=self.reset_agent_memory)，默认仍是 False。 跨问题的上下文改由 sqlite 承担（:1914 / :1716）， 所以「带不带历史」不再需要用牺牲累计口径来换——这正是注释里那句「不传 reset=True」的理由（:1724）。

6.4 E4 故意喂一个错参数 —— 现在不用故意改也会撞

旧版要把 "type": "array" 改成 "number" 才看得见 tools.py:1402 那句报错。 v2.0 基线里 tool_errors 10 次 / 52 次调用（§3.2）——真实模型自己就会传错，不需要你制造。 理解「接口契约由执行方强制」这条，现在直接看审计里那 10 行就行：不是模型遵守，是执行方校验。
